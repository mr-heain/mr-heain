## 1. Introduction

### 1.1 Purpose
This document defines the requirements for **PeerLAN**, a system that transfers files directly between two devices on the same local network, without internet access and without uploading files to any external server. It is the reference for design, development, and testing.

### 1.2 Problem Statement
Sensitive files are often shared through cloud services or messaging apps. These need internet access, store copies on third-party servers, and give the owner no control over where the file goes. In a **closed or offline local network** (for example, a network with no internet connection, or one where outside services must not be used), people still need a simple, private way to move a file from one device to another.

### 1.3 Scope
PeerLAN lets **Device A** (the sender) transfer a file to **Device B** (the receiver) over a local network (WiFi, LAN, or phone hotspot).

**In scope**
- Local session creation and joining using a short code or QR code
- Sender approval before any receiver connects
- Direct device-to-device file transfer
- End-to-end encryption using a shared passphrase
- File integrity verification
- Operation with **no internet connection**
- Receiver access through a normal web browser, with **no installation** on Device B

**Out of scope**
- Transfers across the internet or between different networks
- Cloud storage, accounts, or user registration
- Permanent file storage on any server
- Protecting a file after the receiver has saved it
- Mobile native applications

### 1.4 Definitions, Acronyms, and Abbreviations

| Term | Meaning |
|---|---|
| **Device A** | The sender. Runs the PeerLAN host application. |
| **Device B** | The receiver. Uses only a web browser. |
| **Host application** | The program on Device A that serves the web page and helps the devices find each other |
| **Session / Room** | A temporary, single-use connection context between Device A and Device B |
| **Room code** | A short random code that identifies a session |
| **Passphrase** | A secret entered by both users, used to derive the encryption key |
| **P2P** | Peer-to-peer, meaning data goes directly between devices |
| **WebRTC** | Browser technology for direct device-to-device connections |
| **Data channel** | A WebRTC channel used to send arbitrary data such as file chunks |
| **Signaling** | The exchange of connection-setup messages (offer, answer, ICE candidates) |
| **ICE** | Interactive Connectivity Establishment, the process of finding a network path between devices |
| **DTLS** | Datagram Transport Layer Security, the encryption built into WebRTC |
| **AES-GCM** | Authenticated encryption algorithm used for each file chunk |
| **PBKDF2** | Password-based key derivation function, used to turn the passphrase into a key |
| **SHA-256** | Hash function used to verify file integrity |
| **LAN** | Local Area Network |
| **Relay mode** | Fallback in which encrypted data passes through the host application instead of directly |
| **SRS** | Software Requirements Specification |

## 2. Overall Description

### 2.1 Product Perspective
PeerLAN is a standalone system with two parts:

1. **Host application** on Device A. It serves the web interface over HTTPS and relays connection-setup messages.
2. **Web client** running in the browser on both devices. It handles the user interface, encryption, and file transfer.

File data travels **directly between browsers**. The host application does not receive file data, except in the optional relay fallback, where it forwards **already-encrypted** data only.

```
              Local network (no internet required)

  ┌───────────────┐       Encrypted file chunks       ┌───────────────┐
  │   DEVICE A    │◄════════ direct P2P channel ═════►│   DEVICE B    │
  │ Host app +    │                                   │ Browser only  │
  │ Browser UI    │                                   │ (no install)  │
  └───────┬───────┘                                   └───────┬───────┘
          │ signaling (session setup messages only)           │
          └───────────────────────────────────────────────────┘
```

### 2.2 Product Functions (Summary)
- Start a host application and display access link, QR code, and room code
- Create a time-limited, single-use session protected by a passphrase
- Allow Device B to request to join; Device A approves or rejects
- Establish a direct encrypted connection
- Split, encrypt, send, receive, decrypt, and verify files
- Show progress, speed, and time remaining
- Fall back to relay mode if a direct connection cannot be made
- Optionally record a metadata-only audit log

### 2.3 User Classes and Characteristics

| User | Description | Technical skill |
|---|---|---|
| **Sender (Device A user)** | Starts the host application, shares the code and passphrase, approves the receiver, selects the file | Basic computer use |
| **Receiver (Device B user)** | Opens the link in a browser, enters code and passphrase, receives the file | Basic computer or phone use |
| **Developer / Evaluator** | Builds, tests, and reviews the system | Advanced |

### 2.3.1 Assumptions about users
Users can read a short code, scan a QR code, and type a passphrase. No networking knowledge is assumed.

### 2.4 Operating Environment

| Component | Requirement |
|---|---|
| **Device A OS** | Windows 10/11 or Linux (Ubuntu 22.04 or later); macOS optional |
| **Device B** | Any device with a modern browser (Android, iOS, Windows, Linux, macOS) |
| **Browsers** | Latest stable versions of Chrome, Edge, Firefox, and Safari (to be confirmed in testing) |
| **Network** | Shared WiFi, wired LAN, or phone hotspot; internet **not required** |
| **Ports** | Default port **1212** (configurable); must be allowed through the Device A firewall |

### 2.5 Design Constraints
- Shall work with **no internet access**: no CDN, no external fonts, no STUN/TURN servers.
- Shall use only built-in browser cryptography (Web Crypto API); no custom cryptographic algorithms.
- Shall serve the application over **HTTPS**, because the Web Crypto API and file-saving features require a secure context.
- Shall use only free and open-source software.

### 2.6 Assumptions and Dependencies
- Device A and Device B are on the same local network.
- The network does **not** block device-to-device traffic (client isolation off). If it does, relay mode is used.
- Device A stays powered on and running the host application during the transfer.
- Users accept a one-time browser warning for the locally generated certificate.
- Users share the passphrase through a separate channel (in person, by phone call).

## 3. System Features and Functional Requirements

### 3.1 Host Application Startup

| ID | Requirement | Priority |
|---|---|---|
| FR-01 | The host application shall start an HTTPS server on a configurable port (default 1212). | M |
| FR-02 | The host application shall automatically detect the local network IP address and display the access link. | M |
| FR-03 | The host application shall display a QR code encoding the access link. | M |
| FR-04 | If multiple network adapters exist, the host application shall let the user choose which one to use. | S |
| FR-05 | The host application shall generate a self-signed HTTPS certificate on first run if none exists. | M |
| FR-06 | The host application shall run with no internet connection. | M |
| FR-07 | The host application shall be runnable from the command line on Linux and Windows. | M |

### 3.2 Session (Room) Management

| ID | Requirement | Priority |
|---|---|---|
| FR-08 | Device A shall be able to create a session, producing a random room code of at least 6 characters. | M |
| FR-09 | A session shall expire automatically after a configurable time (default 10 minutes) if no connection is completed. | M |
| FR-10 | A session shall accept only one receiver and shall close after the transfer completes or fails. | M |
| FR-11 | Device A shall set a passphrase when creating a session. | M |
| FR-12 | The system shall limit failed join attempts per device (default 5) and temporarily block further attempts. | M |
| FR-13 | Device A shall be able to cancel and close a session at any time. | M |

### 3.3 Joining and Approval

| ID | Requirement | Priority |
|---|---|---|
| FR-14 | Device B shall be able to open the access link in a browser and enter the room code. | M |
| FR-15 | Device A shall be notified of a join request, showing a device identifier (name or short ID). | M |
| FR-16 | Device A shall explicitly **approve or reject** each join request; no connection shall proceed without approval. | M |
| FR-17 | Device B shall be informed when its request is approved, rejected, or times out. | M |

### 3.4 Connection Establishment

| ID | Requirement | Priority |
|---|---|---|
| FR-18 | The system shall establish a WebRTC data channel between Device A and Device B. | M |
| FR-19 | Signaling messages (offer, answer, ICE candidates) shall be exchanged through the host application. | M |
| FR-20 | The system shall use only local (host) ICE candidates and no external STUN/TURN servers. | M |
| FR-21 | If a direct connection is not established within a timeout (default 15 seconds), the system shall report this and, if enabled, switch to relay mode. | S |
| FR-22 | The system shall show connection status (connecting, connected, failed) on both devices. | M |

### 3.5 Encryption and Integrity

| ID | Requirement | Priority |
|---|---|---|
| FR-23 | Each device shall derive an AES key from the passphrase using PBKDF2 with at least 600,000 iterations (configurable) and a per-session salt. | M |
| FR-24 | The passphrase and derived key shall **never** be sent over the network. | M |
| FR-25 | Each file chunk shall be encrypted with AES-GCM using a unique nonce (never reused with the same key). | M |
| FR-26 | The chunk index shall be included as authenticated data so that reordering, dropping, or duplicating chunks is detected. | M |
| FR-27 | The system shall use a key-check value so that a wrong passphrase fails immediately with a clear message. | S |
| FR-28 | The sender shall compute a SHA-256 hash of the file; the receiver shall verify the received file against it. | M |
| FR-29 | If any chunk fails authentication or the final hash does not match, the transfer shall fail and the file shall be discarded and not saved as complete. | M |

### 3.6 File Transfer

| ID | Requirement | Priority |
|---|---|---|
| FR-30 | Device A shall be able to select a file through a file picker or drag and drop. | M |
| FR-31 | The system shall split the file into chunks of 16 KB to 64 KB. | M |
| FR-32 | The sender shall apply backpressure (monitor `bufferedAmount`) so the data channel is never overloaded. | M |
| FR-33 | Device B shall be shown the file name, size, and type before accepting, and shall be able to accept or decline. | M |
| FR-34 | Both devices shall display progress (percentage), transfer speed, and estimated time remaining. | M |
| FR-35 | Either device shall be able to cancel an ongoing transfer. | M |
| FR-36 | The receiver shall be able to save the completed file to local storage. | M |
| FR-37 | On supported browsers, the receiver shall stream data to disk to support large files; otherwise a configurable in-memory size limit shall apply, with a clear message if exceeded. | S |
| FR-38 | The system shall support transferring multiple files one after another in the same session. | C |
| FR-39 | The system shall support resuming an interrupted transfer. | C |

### 3.6.1 File Name Safety

| ID | Requirement | Priority |
|---|---|---|
| FR-40 | The receiver shall sanitize received file names (remove path separators and unsafe characters) before saving. | M |

### 3.7 Relay Fallback (Optional)

| ID | Requirement | Priority |
|---|---|---|
| FR-41 | In relay mode, encrypted chunks shall be forwarded through the host application over WebSocket. | S |
| FR-42 | In relay mode, the host application shall forward data **without being able to decrypt it** and shall not write it to disk. | S |
| FR-43 | The user interface shall indicate clearly whether the transfer is **direct** or **relayed**. | S |

### 3.8 Audit Log (Optional)

| ID | Requirement | Priority |
|---|---|---|
| FR-44 | The host application shall be able to record, for each transfer: timestamp, file name, size, SHA-256 hash, result, and mode (direct/relay). | C |
| FR-45 | The audit log shall **never** contain file contents or the passphrase. | M (if FR-44 is implemented) |
| FR-46 | The audit log shall be stored locally and exportable as CSV. | C |

### 3.9 Error Handling

| ID | Requirement | Priority |
|---|---|---|
| FR-47 | The system shall show clear, non-technical messages for: invalid or expired code, wrong passphrase, rejected request, connection failure, integrity failure, and cancelled transfer. | M |
| FR-48 | If the connection drops mid-transfer, the system shall notify both users and stop the transfer cleanly. | M |
| FR-49 | After a failed or completed session, all session data (keys, partial buffers) shall be cleared from memory. | M |

## 4. External Interface Requirements

### 4.1 User Interfaces

| ID | Requirement |
|---|---|

## 5. Non-Functional Requirements

### 5.1 Performance

| ID | Requirement | Target |
|---|---|---|
| NFR-01 | Connection setup time on a local network, from approval to channel open | ≤ 5 seconds (typical) |
| NFR-02 | Encryption overhead compared with an unencrypted baseline transfer | ≤ 20% reduction in throughput |
| NFR-03 | Memory use on the receiver when streaming to disk | Does not grow with file size |
| NFR-04 | Supported file size (streaming-capable browsers) | At least 2 GB |
| NFR-05 | Supported file size (browsers without streaming) | Configurable limit (default 200 MB) with a clear message |

*All numeric targets are initial goals and will be validated and adjusted in testing.*

### 5.2 Security

| ID | Requirement |
|---|---|
| NFR-06 | Files shall never be uploaded to any external server. |
| NFR-07 | File contents shall be encrypted end to end; the host application shall not be able to read them in any mode. |
| NFR-08 | Room codes shall be generated with a cryptographically secure random generator. |
| NFR-09 | Nonces shall never repeat for a given key. |
| NFR-10 | Failed authentication shall abort the transfer; partial plaintext shall not be exposed as a completed file. |
| NFR-11 | The host application shall not log passphrases, keys, or file contents. |
| NFR-12 | The system shall rate-limit join attempts and expire sessions to limit guessing attacks. |

### 5.3 Reliability and Availability
- NFR-13: A transfer shall either complete with verified integrity or fail with a clear message; silent corruption is not acceptable.
- NFR-14: The host application shall remain stable across at least 50 consecutive sessions without restart.

### 5.4 Usability
- NFR-15: A first-time user shall be able to complete a transfer in **3 steps or fewer** per device after the link is opened.
- NFR-16: Device B shall require **no installation and no account**.
- NFR-17: Error messages shall avoid technical terms.

### 5.5 Portability and Compatibility
- NFR-18: The web client shall work on the latest stable Chrome, Edge, Firefox, and Safari.
- NFR-19: The host application shall run on Windows 10/11 and Ubuntu 22.04+ (macOS optional).
- NFR-20: The host application shall be distributable as a single executable with no separate runtime installation.

### 5.6 Maintainability
- NFR-21: Code shall be modular (server, signaling, crypto, transfer, UI in separate modules).
- NFR-22: Code shall be commented and stored in version control (Git).
- NFR-23: Cryptographic parameters (iterations, chunk size, timeouts, port) shall be configurable without code changes.

### 5.7 Privacy
- NFR-24: No analytics, tracking, or telemetry shall be included.
- NFR-25: The audit log (if enabled) shall store metadata only.

## 7. System Models

### 7.1 Architecture

```
┌──────────────────────── DEVICE A ────────────────────────┐
│  Host application (Node.js)                              │
│   ├─ HTTPS server ........ serves web client             │
│   ├─ Signaling (WSS) ..... session setup, approval       │
│   ├─ Session manager ..... codes, expiry, rate limits    │
│   ├─ Relay (optional) .... forwards encrypted data       │
│   ├─ Audit log (optional)  SQLite, metadata only         │
│   └─ Cert generator ...... local HTTPS certificate       │
│                                                          │
│  Web client (browser)                                    │
│   ├─ UI                                                  │
│   ├─ WebRTC module ....... connection + chunked sending  │
│   └─ Crypto module ....... PBKDF2, AES-GCM, SHA-256      │
└──────────────────────────────────────────────────────────┘
                 ▲ HTTPS / WSS            ▲ WebRTC (direct)
                 │                        │
┌──────────────────────── DEVICE B ────────────────────────┐
│  Web client (browser): UI + WebRTC + Crypto              │
└──────────────────────────────────────────────────────────┘
```

### 7.2 Sequence: Session Setup and Transfer

```
Device A            Host app             Device B
   │  create session   │                    │
   │──────────────────►│                    │
   │◄── room code ─────│                    │
   │                   │◄── join(code) ─────│
   │◄─ join request ───│                    │
   │── approve ───────►│                    │
   │                   │── approved ───────►│
   │◄═══ offer / answer / ICE (via host app) ═══►│
   │                                         │
   │◄═════ direct WebRTC channel open ═════►│
   │   derive key (PBKDF2) on both sides     │
   │── key-check ───────────────────────────►│
   │── file info ───────────────────────────►│
   │◄─ accept ──────────────────────────────│
   │══ encrypted chunks (AES-GCM) ══════════►│
   │── final SHA-256 ───────────────────────►│
   │◄─ verified / saved ────────────────────│
   │   close session, clear keys             │
```

### 7.3 Data Flow (Transfer)

```
File → split into chunks → AES-GCM encrypt (key from passphrase)
     → send over data channel (with backpressure)
     → receive → AES-GCM decrypt + authenticate → reassemble
     → SHA-256 verify → save
```

### 7.4 Session State Model

```
CREATED ─► WAITING ─► REQUESTED ─► APPROVED ─► CONNECTING ─► CONNECTED
   │          │           │            │            │             │
   │          ▼           ▼            ▼            ▼             ▼
   └──────► EXPIRED   REJECTED     CANCELLED    FAILED ──► (relay?) 
                                                                │
                                              TRANSFERRING ◄────┘
                                                   │
                                      COMPLETED / FAILED / CANCELLED ─► CLOSED
```

## 8. Data Requirements

| Data | Where kept | Lifetime |
|---|---|---|
| Room code, session state | Host application memory | Until session closes or expires |
| Passphrase | Users' memory and browser memory only | Cleared when session ends |
| Derived AES key | Browser memory only | Cleared when session ends |
| File content | Sender's disk (original), receiver's disk (saved copy), in transit only between | Not stored by the host application |
| TLS certificate | Local data folder next to the executable | Persistent, regenerable |
| Audit log (optional) | Local SQLite file | Persistent until deleted by user |

**Audit log fields:** timestamp, file name, size, SHA-256 hash, mode (direct/relay), result (success/failure).

## 9. Constraints, Assumptions, and Dependencies

### 9.1 Known Technical Constraints and Planned Handling

| Constraint | Handling |
|---|---|
| WebRTC messages should be small | Use 16 to 64 KB chunks |
| Fast sender can overload the channel | Backpressure using `bufferedAmount` |
| Large files can exhaust browser memory | Stream to disk where supported; limit otherwise |
| Web Crypto requires a secure context | Serve over HTTPS with a locally generated certificate |
| Some networks block device-to-device traffic | Relay fallback |
| Some phones leave WiFi networks without internet | Document a user setting; test on Android and iOS |
| Hostnames for local devices may not resolve on some networks | Relay fallback; test early |

### 9.2 Security Limitations (Accepted)
- The system protects data **in transit** only. It cannot prevent a receiver from copying or forwarding a file after saving it.
- It cannot protect a device that is already compromised.
- Security depends on the passphrase strength and on sharing it through a separate channel.

## 11. Risks

| ID | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| R1 | Network blocks device-to-device traffic | Medium | High | Early testing; relay fallback |
| R2 | WebRTC learning curve delays progress | Medium | Medium | Prototype a two-device text and file demo first |
| R3 | Browser differences (especially iOS Safari) | Medium | Medium | Defined supported list; early testing |
| R4 | Cryptographic implementation error | Medium | High | Use only Web Crypto API; unique nonces; unit tests |
| R5 | Unsigned executable flagged by antivirus | Medium | Low | Provide source-run and Linux versions as backup |
| R6 | Scope growth | High | Medium | Fixed Must list; optional features only after testing passes |
| R7 | Self-signed certificate warning confuses users | High | Low | Clear instructions in user guide |
